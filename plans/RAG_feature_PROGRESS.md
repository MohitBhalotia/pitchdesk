## Behavior changes made along the way (not silent — flagging explicitly)

1. **`start-pitch` and `/api/authenticate` now require a valid NextAuth session.** A request with no session gets 401; a session whose user doesn't match a supplied body `userId` gets 403. Previously both endpoints trusted the body `userId` outright — this was the exact gap Phase 0 named. Any legitimate logged-in client is unaffected since the frontend already sends the real session's user.
2. **Converged an inconsistency between `end-pitch` and Inngest's `updatePitch`** that existed before this refactor: `end-pitch` silently no-opped when an incubation pitch had no matching `IncubationParticipant` record, while Inngest's version returned a hard failure for the same case. The shared `deductPitchCredits` now always throws `INCUBATION_PARTICIPANT_NOT_FOUND` (the stricter of the two), so both paths agree.
3. **Inngest's periodic `update-pitch` (fired every 10s during an active session) no longer requires a `UserPlan` document to exist for competition/incubation pitches.** The old code fetched and required a `userPlanModel` row up front for every pitch type, even though competition/incubation deductions don't touch it. The shared function now only requires one where it's actually used (plain practice pitches, and the practice-competition branch) — matching `end-pitch`'s always-worked behavior, which governs session-ending and is authoritative for credits.

None of these change what a normal, currently-logged-in founder experiences; they close a real trust gap and remove a real inconsistency. Flagging in case anything downstream (e.g. a saved test account with a stale session) surfaces an edge case.

## Assumptions and scope decisions made without asking (flag if wrong)

- **Fact-conflict threshold:** two active facts for the same (metric, period, actual/projected/historical) are flagged as conflicting when they differ by more than 5%. Arbitrary but reasonable; easy to tune in `src/lib/ingestion/factConflicts.ts`.
- **Chunk token budget:** 650-token soft target, 800 hard ceiling, 100-token overlap (middle of the plan's 500-800/80-120 ranges), using `gpt-tokenizer`'s cl100k_base encoding (matches `text-embedding-3-small`). A single normalized element already over 800 tokens on its own is kept whole rather than force-split mid-sentence.
- **Duplicate detection:** the plan calls for a "duplicate content hash" check but doesn't specify the algorithm. For uploaded files this uses Cloudinary's `etag` (avoids re-downloading a file just to hash it); for pasted text it's a real SHA-256 of the trimmed text. The worker rejects (non-retryably) a new source whose hash matches an already-`ready` source in the same room.
- **Fact extraction cost/granularity:** `extractStartupFacts` runs once per chunk rather than once per document, so a large document makes one OpenAI call per chunk. Simpler and more parallel-friendly, but costlier than batching — worth revisiting once there's real usage data (this is exactly what Section 7's eval harness and Section 5's cost tracking, both later phases, are for).
- **Added `gpt-tokenizer` as a new dependency** (pure JS, no native/WASM bindings) specifically for accurate token-budgeted chunking — a char-count approximation would have avoided the dependency but made the 500-800 token targets much less precise.
- Did not build a dedicated "delete-source" BullMQ queue — deletion (Cloudinary destroy + chunk/fact cleanup) runs synchronously in the API route. Sources are capped at 20/room, so this isn't a hot or slow path; revisit if that changes.

## Assumptions and scope decisions made in Phase 3 (flag if wrong)

- **`search_previous_pitch_memory` is a stub in this phase.** The plan's Section 2 tool-calling contract names exactly three fixed tools, and Phase 4 is the phase that actually builds `RoomMemory`. Rather than omit the tool (breaking the "exactly three tools" contract) or build memory early (out of Phase 3's named scope), it's registered and fully wired through the auth/circuit-breaker envelope now, and always answers `{found: false, reason: "no_prior_session_memory"}` until Phase 4 gives it something to search.
- **The room pitch-session page lives at `/pitch-rooms/[roomId]/pitch`, nested inside the existing `(root)` app shell (sidebar + topbar), not a full-screen kiosk experience like generic `/start-pitch`.** The generic flow's immersive full-screen page works by defining its own root-level `layout.tsx` with a second `<html>`/`<body>` — that's only possible because `start-pitch` is a top-level route segment; `pitch-rooms` is already a segment under `(root)`, and creating a second, differently-styled top-level `pitch-rooms` directory would collide with the existing one (same URL segment, two conflicting layout trees). Functionally identical (same mic/socket/tool mechanics); a distraction-free shell for room sessions is a reasonable follow-up if you want the same kiosk feel as generic pitching.
- **Retrieval-result cache key includes `knowledgeBaseRevision` but chunk *queries* never filter on it.** Confirmed against the actual Phase 2 ingestion code (`worker/src/ingestion/runIngestSourceJob.ts`): each new source's chunks are stamped with the revision active *at ingestion time* and never re-tagged when the KB's `activeRevision` bumps again later, so a `knowledgeBaseRevision` filter on read would silently hide older sources' content. Revision is used purely to invalidate the retrieval cache on new ingestion, matching Section 4's literal cache-key spec and the Atlas index definition (which also has no revision filter field).
- **Circuit-breaker and token-validation state live in Redis first, Mongo as fallback/audit trail**, per Section 4's "cache is an optimization, never a correctness dependency" rule — if Redis is down, every tool call costs one extra Mongo round trip but behaves identically; nothing breaks or leaks isolation.
- **Room-session token TTL = founder's remaining pitch minutes + a 5-minute grace buffer, hard-capped at 3 hours** in `roomToolSession.ts` regardless of what the caller passes — a forged or stale "remaining time" value can never mint a token that meaningfully outlives a normal pitch.
- **Did not touch `middleware.ts`'s auth-redirect logic.** Pre-existing behavior (predates Phase 3): `protectedRoutes.includes(url.pathname)` only exact-matches, so entries like `"/pitch-rooms/:path*"` never actually match a real nested path like `/pitch-rooms/<id>/pitch` — meaning middleware won't redirect an unauthenticated visitor to `/login` for nested room routes (it does for the base `/pitch-rooms`). This is not a security gap (every API route independently enforces the NextAuth session via `resolveSessionUserId`, returning 401), only a UX one — an unauthenticated visitor hitting the URL directly sees a broken page instead of a login redirect. Same pre-existing gap already applied to `/pitch-rooms/[roomId]` before this phase; left alone since fixing shared middleware matching logic touches every protected route in the app and is outside Phase 3's named scope.

## Assumptions and scope decisions made in Phase 4 (flag if wrong)

- **"Forget this session" deletes only the `RoomMemory` record, not the underlying `Pitch`.** The plan names both "deleting a pitch deletes its derived memory" (pitch → memory cascade, implemented in `/api/my-pitches` DELETE) and a separate room Memory view with a "Forget this session" action -- read as two distinct entry points into the same cleanup, not the same action twice. Forgetting a memory leaves the pitch/transcript exactly as visible in My Pitches/evaluation as before; only future prompts stop recalling it.
- **No standalone Redis "room memory digest cache."** Section 4 names one keyed `roomId + latestPitchId`, but the computed digest is stored directly on the `PitchRoom` document (source of truth) and the session-start route already has that document in hand for ownership/KB checks -- a cache in front of a field that's already free to read would be pure unused abstraction. If a future consumer needs the digest without already holding the room document, add the cache then.
- **The abandoned-pitch sweep is a `setInterval` inside the long-lived worker process, not a new BullMQ repeatable/cron job.** The plan's "two job systems" split is about durable per-item async work (BullMQ) vs. existing app jobs (Inngest); the sweep itself is neither -- it's a trivial periodic Mongo query whose only job is to enqueue real per-pitch recovery work onto the existing `recover-abandoned-room-pitch` queue (which does have full BullMQ retry/dedup semantics). Introducing a new scheduling primitive just to trigger a query seemed like unnecessary infra for what it does.
- **Staleness threshold: 5 minutes since `lastUpdated`.** The existing Inngest `updatePitch` heartbeat already fires every 10s during any active session (generic or room) and already sets `pitch.lastUpdated` -- 5 minutes of silence is ~30 missed heartbeats, comfortably past any transient network hiccup while still catching a genuinely abandoned tab reasonably quickly. Arbitrary but reasonable; both the sweep and the recovery job's own defensive re-check use the same constant.
- **Recovered pitches use `lastUpdated` (last known-good heartbeat), not "now," as the effective `endTime`/duration boundary.** Charging a founder for the silent gap between their last heartbeat and whenever the sweep happens to run would overcharge them for time they weren't actually pitching.
- **Memory extraction runs once per completed pitch, in one OpenAI call over the full transcript** (bounded to 20,000 input chars, output categories capped at 8 items each) -- simpler than per-message extraction and the transcript itself is never stored past this call, only the bounded output. Worth revisiting with real usage/cost data, same as the analogous per-chunk-vs-per-document tradeoff already flagged in Phase 2's fact extraction.
